# Package: simplysmart/mainboard

## Context & Responsibility
Standalone Laravel Composer package (`laravel/framework` ^13): the **Application Core** of simplysmart applications — everything shared by the zones (contracts, base classes, DTOs, layouts and UI components, the shared localization middleware and the common zone mechanisms), kept out of the skeleton so it stays stock Laravel. Mainboard is not a zone: it has no users table, guard or zone slug of its own; zone packages build on its contracts. Developed inside the skeleton at `packages/simplysmart/mainboard/` (symlinked into its `vendor/`), but it is its own Git repository and must work without the skeleton.

## Architectural Boundaries
- **No application coupling**: Never reference skeleton classes (`App\...`) or other packages' concrete classes. Depend on contracts; receive dependencies through constructor injection or the container.
- **Contracts**: All contracts/interfaces of this package MUST reside in `src/Contracts/` (`Simplysmart\Mainboard\Contracts\*`). Bind their implementations in the `register()` of the area provider that owns them (`src/Providers/`).
- **Service Providers**: `src/MainboardServiceProvider.php` is the only auto-discovered provider (`extra.laravel.providers`): it merges config, wires texts/localization, loads resources (migrations, views, translations) and registers the area providers in `src/Providers/` (`ZonesServiceProvider`, `SignInServiceProvider`, `PermissionsServiceProvider`, `AuditServiceProvider`, `SecurityServiceProvider`). A new area gets its own provider there instead of growing the main one. Keep these files inside the package, never in the skeleton.
- **Configuration**: Own settings live in `config/mainboard.php`, read only via `config('mainboard.key')`; `env()` only inside that file. Never publish it into the skeleton (override through `.env`). Extend framework config (e.g. log channels, mail options) with `config([...])` in the provider, never by editing the skeleton's `config/` (see the skeleton's "Framework Footprint").
- **Laravel-like layout and overrides**: Resources live in `resources/views/` and `lang/` and are registered with `loadViewsFrom(..., 'mainboard')` / `loadTranslationsFrom(..., 'mainboard')`; use them as `view('mainboard::...')` and `__('mainboard::...')`. The skeleton may override a single file in `resources/views/vendor/mainboard/` or `lang/vendor/mainboard/<locale>/` (it wins over the package, even when empty); write new views here, never in the skeleton, and never bulk-publish them (see the skeleton's "Framework Footprint"). Zone-specific views belong to their zone packages, not to Core. Framework translations without a namespace (`validation.*`, `auth.*`, `passwords.*`, `pagination.*`) live in `lang/<locale>/` and are inserted by `CoreTranslationPath` between the framework's and the application's `lang/` path, so the skeleton overrides them in `lang/<locale>/<file>.php`. `lang/` is also registered as the `mainboard` namespace for the `text_*` cascade (zone package → mainboard → skeleton → key, no fallback language; `Contracts\TextTranslator`, groups in `Translation\TextGroup`). In UI code use `text_*` / `local_*` (`src/helpers.php`), not `__()`; a new text family is a new `TextGroup` case plus one helper.
- **Assets**: Static CSS without a bundler in `public/assets/` (see `docs/struktura.md`); brand sources in `brand/`.
- **Design system**: UI follows `docs/design-system.md` (concept: Clean & Soft Enterprise, graphite accent, semantic `--ss-*` tokens only, no `dark:` classes in views).
- **Build (concept, `docs/design-system.md` §8)**: every package, Core included, gets its own `package.json` (npm workspace `@simplysmart/<package>`) and `vite.config.js` (Tailwind 4) building into its own `public/build/`. The skeleton runs them all with one `npm run dev|build` through the orchestrator from `simplysmart/tools`; never add a package to the skeleton's `vite.config.js` or `package.json`. Served via `php artisan mainboard:assets` (`public/vendor/<package>`), loaded with `x-mainboard::assets`, not `@vite`.

## Security & Multi-Zone Isolation
Zones are isolated sandboxes (own users table, guard and session). The skeleton's `CLAUDE.md` section "Multi-Zone Isolation" is the source of truth. Core provides the shared mechanisms; zone packages configure them. In short:
- **Isolated guards**: Core code never assumes a guard: it receives the zone's guard (from the zone's config or a contract) and always names it (`Auth::guard($guard)`, `auth:<zone-guard>`). Never rely on the default `Auth::user()` or `auth.defaults.guard`.
- **Session isolation**: Core's session middleware sets the zone's cookie name (and path/domain where zones differ) before `StartSession`, so concurrent logins in different zones keep working.
- **Zone mechanism** (`docs/strefy.md`): zone packages extend `Zones\ZoneServiceProvider`; Core registers the guard, the `zone.<zone>` middleware group (replaces `web`) and the routes per access tier (`public.php`, `account.php`, `zone.php`). Read the request's zone from `Contracts\CurrentZone` and its signed-in account from `Contracts\CurrentAccount`, never from static state or a guard you look up yourself; account identifiers go through `Auth\AccountKey`, and a zone account's cached roles are reset with `forgetZonePermissions()`. Sign-in (e-mailed code + PIN) is Core's: zone account models extend `Models\ZoneAccount` (via `MainAuthenticatable`: standard columns, checksum, soft delete, like `DataModel`), zone tables come from `Database\ZoneTables` (accounts with standard columns, `<zone>_accounts_history` and id slots), new steps implement `Contracts\SignInStep` and are listed in `auth.steps`; every failure shows `SignInFailure`'s single message; sign-in views read their texts only through `ZoneDefinition::signInText()` (zone-specific `<texts>::sign_in.<zone>.*`, then package, then Core), so zone packages customise headings, leads and notes without overriding views. Zones without registration create accounts with a command extending `Console\CreateZoneAccountCommand` (action `Auth\CreateZoneAccount`). Revoking an account's access (sessions, trusted devices) goes only through `Auth\RevokeAccountAccess`; admin actions on accounts are `Auth\AccountAdministration` and run in the account's zone (`Zones\AccountZone`); code acting in another zone than the request uses `CurrentZone::within()`. Zone pages use the layout `x-mainboard::zone.layout` (Core shares `$zone` and the signed-in `$account`; for a signed-in account it renders the application layout, with the zone's menu, search and subtitle from its `Contracts\ZoneNavigation` registered in `Zones\ZoneNavigations`); the application layout with a collapsible side menu and global search is `x-mainboard::app.layout` (`View\Navigation\*` value objects); zone packages add their own design system previews through `Contracts\DesignSystemCatalog`; every layout builds on the base template `x-mainboard::page` (meta title, description, keywords, tags, robots) instead of its own `<head>`.
- **Bots & errors**: error masking (`Security\ErrorMasker`, 401/403/405/419/429 → 404, production by default, zone `security.mask_errors`), AI agents blocked per zone (`security.block_ai_agents`), optional honeypot (`mainboard.honeypot`: trap routes registered after all providers, form trap `x-mainboard::honeypot`, bans keyed only by an IP hash).
- **Cookie consent**: the banner and settings `x-mainboard::cookie-consent` live in the base template (every page of every zone) and show only with a published policy (`Cookies\CookiePolicies`, versions in `cookie_policies`) or a registered optional script; packages describe their cookies in `Contracts\CookieCatalog` and register scripts that need consent in `Contracts\ConsentScripts` (never load such a script directly). Consents go only through `Cookies\ConsentRegistry` (`cookie_consents`, no IP or personal data); policy Markdown is rendered only through `Cookies\PolicyMarkdown` (raw HTML stripped).
- **Audit**: every audited event maps to an entry only in `Audit\AuditEntries` (file log and `audit_events` table); panels record their own actions with `Audit\Events\AdminActionPerformed`. No e-mail addresses in entries.
- **Cache isolation**: Build zone cache keys only with `Zones\ZoneCacheKey`. Prefix cache keys with the zone (`zone:<zone>:...`) while the store is `database`; use `Cache::tags(['zone:<zone>', ...])` only on `redis` (`database` and `file` stores do not support tags). Never call a global `Cache::flush()`.

## Database & Models
`docs/baza-danych.md` is the source of truth (its status line says what is implemented). In short:
- **One place**: migrations of every table (Core and public zones) live in this package's `database/migrations/`; private packages keep their own (skeleton's `CLAUDE.md`, "Private Packages": nothing about them in this public repository, examples use neutral names such as `shop`), loaded by `MainboardServiceProvider`; seeders are classes in `src/Database/Seeders/` run by Core commands (`mainboard:localization:seed`). Production blocks destructive DB commands; demo seeders refuse to run there.
- **Schema**: `Columns::base($table)` → domain columns → `Columns::closing($table, i18n: ...)` (`Database\Columns`, plain static methods — no Blueprint macros), then `app(History::class)->create($table)` (`<table>_history`; `->sync()` after column changes, `->drop()` in `down()`) and `app(IdSlots::class)->reserve($table)` (user ids from 1000, seed slots 1–999 via `IdSlots::next()`); `closing()` adds the global `json_default_settings` (read via `defaultSetting()`) and `json_tags`; `status` is a string backed by a PHP enum, flags are `boolean()` + `'boolean'` cast. Link tables have no standard columns but have history.
- **Models**: extend `Models\DataModel` (token, soft delete, standard casts, checksum, scopes `active()` and `default()` over the standard `is_active`/`is_default` flags; `HasI18n` for `json_i18n`); columns with a DB default repeat it in `$attributes`; no business logic and no `Auth` in models, no queries in controllers (`Queries/`, `Actions/`); every column has a cast and a `text_data` label (`lang/<locale>/data.php`); relations only in traits (`Models/Relations/`); public URLs use `token`, never `id`.
- **Organizations & permissions** (§15): `spatie/laravel-permission` with teams = `Models\Organization` (`organization_id`), configured by `Permissions\PermissionDefaults` (never publish `config/permission.php`); Core models `Models\Permissions\{Role,Permission,PermissionDenial}` with the full data standard on roles/permissions; zone accounts get roles and denials via `HasZonePermissions` (denial wins); check through `Contracts\ZonePermissionChecker` with the zone's guard. No default organization (fail closed): the zone middleware `UseCurrentTeam` sets the request's organization (operator organization `Organization::OPERATOR_ID` for zones without `teams`, otherwise the account's chosen membership in `organization_members`); global roles need an explicit `organization_id => null`. Zone roles come only from JSON files (`database/seeders/permissions/<zone>.json`, private packages register their own via `PermissionFiles::add()`) synced by `mainboard:permissions:sync`; protect routes with `ZonePermission::middleware()`, records of one organization extend `Models\OrganizationDataModel`, roles are granted only through `ZoneRoleAssignment` (no escalation, except roles delegated by the assigner's own roles in that organization: `assigns` in the roles file, `Permissions\RoleDelegation`; `SystemRoleGrant` only for console and provisioning). Organizations change only through `Organizations\OrganizationManagement` (no tree cycles, operator organization protected); people join an organization through `Organizations\EnrollMember`.
- **Localization dictionaries** (§14): tables `locale_*`, ISO columns `alpha_code_2`/`alpha_code_3`/`numeric_code` (`Database\CodeColumns`, `Contracts\DictionaryEntry::codeColumn()`), countries with ICU territory data (`Enums\Continent`, M49 region, population) sorted by continent; `Models\Dictionaries\{Country,Language,Currency,TaxRate,ExchangeRate}`, reads via `Queries\Dictionaries\{DefaultEntries,TaxRatesInForce,ExchangeRatesOn}`; days off per country come only from `Contracts\HolidayProvider` (Nager.Date) through `Holidays\HolidaySync` or `Holidays\ManualHolidays` and are read through `Queries\Dictionaries\HolidaysIn` (calendars mark them with `.ss-calendar__day--holiday`); exchange rates (PLN-based) come only from `Contracts\ExchangeRateProvider` (NBP table A) through `ExchangeRates\ExchangeRateSync` or `ExchangeRates\ManualExchangeRates`; interface languages via `Contracts\InterfaceLocales`, always within `APP_LOCALES`.

## Routing & URL Conventions
The skeleton's `CLAUDE.md` section "Routing & URL Conventions" is the source of truth; in short:
- **Clean signatures**: Controllers, actions and Form Requests never accept `$locale` or a zone slug; use `App::getLocale()`.
- **Shared localization**: Core owns the single localization middleware (`App::setLocale()`, `URL::defaults()`, `forgetParameter('locale')`) and the locale-mode logic (one locale → no prefix; several → `{locale}` always). Zone packages only attach it.
- **Core routes**: Any route of Core itself is defined in `routes/web.php` (relative paths, short names) and registered by `Providers\CoreRoutesServiceProvider` with the fixed name prefix `mainboard.`, the `{locale}` prefix from `Localization\LocaleRouting::prefix()`/`where()` (shared with zones) and `SetLocale` + `SecurityHeaders` (no session); e.g. the design system page `mainboard.design-system`, enabled outside production (`DESIGN_SYSTEM_PAGE`), checked per request; zone slugs and zone route-name prefixes belong to the zone packages.
- **Named routes only**: Generate links with `route()`, never hand-built URLs containing the locale or slug.

## Development Rules
- **Strict Typing**: Every PHP file starts with `declare(strict_types=1);` (enforced by Pint).
- **Coding Standards**: PHP ^8.4, PSR-4 (`Simplysmart\Mainboard\` → `src/`), PER Coding Style via Laravel Pint `per` preset (`pint.json`).
- **Dependencies**: Follow `docs/zaleznosci.md` (MIT-compatible licences, `^` ranges, update the table and `CHANGELOG.md`). `composer.lock` is not committed.
- **Changelog**: Record user-visible changes in `CHANGELOG.md` under `## [Unreleased]` (Keep a Changelog; see `CONTRIBUTING.md`).

## Testing & Quality
Run in this directory before finishing:
- `composer lint` — style and strict types (`composer format` fixes them).
- `composer analyse` — PHPStan at level `max` (`phpstan.neon`). Fix the cause; no ignores or baseline.
- No package test suite yet; integration with the skeleton is covered by the skeleton's `tests/Feature/PackageIntegrationTest.php` (`composer test` in the skeleton root).

## Releasing
From the skeleton root: `vendor/bin/version-release --root=packages/simplysmart/mainboard` (add `--dry-run` to preview without changing files). It really releases — never run it without `--dry-run` just to test.
