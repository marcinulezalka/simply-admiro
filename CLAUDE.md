# Package: simplysmart/admiro

## Context & Responsibility
Standalone Laravel Composer package (`laravel/framework` ^13) with three parts: (1) the **Application Core** of simplysmart applications — the database (migrations of every public table), everything shared by the zones (contracts, base classes, DTOs, layouts and UI components, the shared localization middleware and the common zone mechanisms), kept out of the skeleton so it stays stock Laravel; (2) the **administrators' zone** `admiro` in `src/Panel/`, built on the Core zone mechanism like any other zone; (3) the **developer toolbox** in `src/Tools/`. The Core itself is not a zone: it has no users table, guard or zone slug of its own. Until 0.3.0 the Core was the separate package `simplysmart/admiro`; its history is merged into this repository. Developed inside the skeleton at `packages/simplysmart/admiro/` (symlinked into its `vendor/`), but it is its own Git repository and must work without the skeleton.

## Architectural Boundaries
- **No application coupling**: Never reference skeleton classes (`App\...`) or other packages' concrete classes. Depend on contracts; receive dependencies through constructor injection or the container.
- **Contracts**: All contracts/interfaces of this package MUST reside in `src/Contracts/` (`Simplysmart\Admiro\Contracts\*`). Bind their implementations in the `register()` of the area provider that owns them (`src/Providers/`).
- **Service Providers**: two providers are auto-discovered (`extra.laravel.providers`), Core first: `src/AdmiroServiceProvider.php` merges config, wires texts/localization, loads resources (migrations, views, translations) and registers the area providers in `src/Providers/` (`ZonesServiceProvider`, `SignInServiceProvider`, `PermissionsServiceProvider`, `AuditServiceProvider`, `SecurityServiceProvider`). A new area gets its own provider there instead of growing the main one. `src/Panel/PanelServiceProvider.php` registers the administrators' zone (see below). Keep these files inside the package, never in the skeleton.
- **Configuration**: Own settings live in `config/admiro.php`, read only via `config('admiro.key')`; `env()` only inside that file. Never publish it into the skeleton (override through `.env`). Extend framework config (e.g. log channels, mail options) with `config([...])` in the provider, never by editing the skeleton's `config/` (see the skeleton's "Framework Footprint").
- **Laravel-like layout and overrides**: Resources live in `resources/views/` and `lang/` and are registered with `loadViewsFrom(..., 'admiro')` / `loadTranslationsFrom(..., 'admiro')`; use them as `view('admiro::...')` and `__('admiro::...')`. The skeleton may override a single file in `resources/views/vendor/admiro/` or `lang/vendor/admiro/<locale>/` (it wins over the package, even when empty); write new views here, never in the skeleton, and never bulk-publish them (see the skeleton's "Framework Footprint"). Zone-specific views belong to their zone packages, not to Core. Framework translations without a namespace (`validation.*`, `auth.*`, `passwords.*`, `pagination.*`) live in `lang/<locale>/` and are inserted by `CoreTranslationPath` between the framework's and the application's `lang/` path, so the skeleton overrides them in `lang/<locale>/<file>.php`. `lang/` is also registered as the `admiro` namespace for the `text_*` cascade (zone package → admiro → skeleton → key, no fallback language; `Contracts\TextTranslator`, groups in `Translation\TextGroup`). In UI code use `text_*` / `local_*` (`src/helpers.php`), not `__()`; a new text family is a new `TextGroup` case plus one helper.
- **Glossary (wiki)**: terms live only in `Wiki\Wiki` (Core terms in `AdmiroServiceProvider::WIKI`, texts `lang/<locale>/wiki.php`; packages add their own with `add($key, $icon, '<package>::')`), ids carry the `wiki-` prefix (`WikiEntry::id()`), shown with `x-admiro::wiki-tip term="…"` (icon, tag, keyword, definition, optional „Jak korzystać” `.usage`, example).
- **Assets**: Static CSS without a bundler in `public/assets/` (see `docs/struktura.md`); brand sources in `brand/`.
- **Design system**: UI follows `docs/design-system.md` (concept: Clean & Soft Enterprise, graphite accent, semantic `--ss-*` tokens only, no `dark:` classes in views).
- **Build (concept, `docs/design-system.md` §8)**: every package, Core included, gets its own `package.json` (npm workspace `@simplysmart/<package>`) and `vite.config.js` (Tailwind 4) building into its own `public/build/`. The skeleton runs them all with one `npm run dev|build` through the orchestrator from the developer tools in `simplysmart/admiro`; never add a package to the skeleton's `vite.config.js` or `package.json`. Served via `php artisan admiro:assets` (`public/vendor/<package>`), loaded with `x-admiro::assets`, not `@vite`.

## Security & Multi-Zone Isolation
Zones are isolated sandboxes (own users table, guard and session). The skeleton's `CLAUDE.md` section "Multi-Zone Isolation" is the source of truth. Core provides the shared mechanisms; zone packages configure them. In short:
- **Isolated guards**: Core code never assumes a guard: it receives the zone's guard (from the zone's config or a contract) and always names it (`Auth::guard($guard)`, `auth:<zone-guard>`). Never rely on the default `Auth::user()` or `auth.defaults.guard`.
- **Session isolation**: Core's session middleware sets the zone's cookie name (and path/domain where zones differ) before `StartSession`, so concurrent logins in different zones keep working.
- **Zone mechanism** (`docs/strefy.md`): zone packages extend `Zones\ZoneServiceProvider`; Core registers the guard, the `zone.<zone>` middleware group (replaces `web`) and the routes per access tier (`public.php`, `account.php`, `zone.php`). Read the request's zone from `Contracts\CurrentZone` and its signed-in account from `Contracts\CurrentAccount`, never from static state or a guard you look up yourself; account identifiers go through `Auth\AccountKey`, and a zone account's cached roles are reset with `forgetZonePermissions()`. Sign-in (e-mailed code + PIN) is Core's: zone account models extend `Models\ZoneAccount` (via `MainAuthenticatable`: standard columns, checksum, soft delete, like `DataModel`), zone tables come from `Database\ZoneTables` (accounts with standard columns, `<zone>_accounts_history` and id slots), new steps implement `Contracts\SignInStep` and are listed in `auth.steps`; every failure shows `SignInFailure`'s single message (sign-in validation errors are global toasts via `View\Toast::fromErrors()`, fields are not marked); sign-in views read their texts only through `ZoneDefinition::signInText()` (zone-specific `<texts>::sign_in.<zone>.*`, then package, then Core), so zone packages customise headings, leads and notes without overriding views. Zones without registration create accounts with a command extending `Console\CreateZoneAccountCommand` (action `Auth\CreateZoneAccount`). Revoking an account's access (sessions, trusted devices) goes only through `Auth\RevokeAccountAccess`; the screen lock (Win+L: the account stays signed in, every signed-in page leads to the PIN screen until the PIN is entered) only through `Auth\ScreenLock` (`account.lock`/`account.unlock`, `Http\Middleware\EnsureScreenUnlocked` in the Authenticated tier, PIN through `PinVerifier`); the recovery e-mail (security page) and the self-service PIN reset on the forgot-PIN page go only through `Auth\Recovery\RecoveryEmailRegistration` / `RecoveryPinReset`, their codes only through `Auth\Recovery\SessionCodes` (zone session, per purpose, never the sign-in challenge table); admin actions on accounts are `Auth\AccountAdministration` and run in the account's zone (`Zones\AccountZone`); code acting in another zone than the request uses `CurrentZone::within()`. Zone pages use the layout `x-admiro::zone.layout` (Core shares `$zone` and the signed-in `$account`; for a signed-in account it renders the application layout, with the zone's menu, settings groups, search and subtitle from its `Contracts\ZoneNavigation` registered in `Zones\ZoneNavigations` (the menu may pick the layout variant per request with `Contracts\ZoneAppLayout`, e.g. Workspace in one role context); settings pages switch the side menu to the settings menu built by `Zones\ZoneSettingsMenu` — zone groups, then Core's account group with profile, security and appearance (theme, palettes, text size, content width and the zone's typefaces `font_styles`, kept by the browser in `js/theme.js`, or — in a zone with `appearance.account` — by the account through `Profile\AccountAppearance`: the zone's `appearance.defaults` overridden by the account's choices per active role in `json_attributes.appearance.<role>` (`*` without a role), drawn on `<html>` by the server, saved by `js/theme.js` on `account.appearance.update`) — with a way back; session messages are toasts via `View\Toast::fromFlash()`; PIN inputs use `x-admiro::pin-field` with its on-screen keypad); the application layout with a collapsible side menu and global search is `x-admiro::app.layout` (`View\Navigation\*` value objects); zones other than the administrators' use the separate base layout `x-admiro::app.zone-layout` (`Enums\AppLayout::Zone`: back/change-context/sign-out link above the title — `home` on start pages —, footer with the account menu of profile and sign-out only, search with „+”, lightning `SearchBox::$findActions` (at its bottom the `/` command field: `Enums\QuickCommand`, default `todo:` — account TODO tasks `account_tasks` written only through `Tasks\AccountTasks`, read through `Queries\Tasks\AccountTaskList`, routes `account.tasks.*`) and scopes, context switch with indented roles, the date opening the calendar and notifications side panels as an accordion (notifications ~60% of the height, the account's TODO list `x-admiro::app.tasks` ~40% below), no sitemap; `Contracts\ZonePageProgress` draws „TEMP” over unfinished views; `docs/design-system.md` §5; its variant `Enums\AppLayout::Columns` keeps the header and footer and splits the content into `x-admiro::app.columns` — the left menu of the page, viewport-high with its own (touch) scrolling (slot `left`, on settings pages the settings categories `x-admiro::app.settings-nav`), the content and the pinnable right sidebar `x-admiro::app.sidebar-wiki`, opened by the „Wiki” tile in the calendar panel tools, with the account's TODO list under the wiki — a page's wiki and tips go only into its `sidebar-wiki` slot, never into the content; folder quick actions — lightning with Save/Cancel beside `.ss-folders` tabs — are `x-admiro::folder-actions`) — never add its features to the Workspace layout of the administrators' zone; zone packages add their own design system previews through `Contracts\DesignSystemCatalog`; every layout builds on the base template `x-admiro::page` (meta title, description, keywords, tags, robots) instead of its own `<head>`.
- **Bots & errors**: error masking (`Security\ErrorMasker`, 401/403/405/419/429 → 404, production by default, zone `security.mask_errors`), AI agents blocked per zone (`security.block_ai_agents`), optional honeypot (`admiro.honeypot`: trap routes registered after all providers, form trap `x-admiro::honeypot`, bans keyed only by an IP hash).
- **Cookie consent**: the banner and settings `x-admiro::cookie-consent` live in the base template (every page of every zone) and show only with a published cookie policy (`LegalDocumentType::Cookies`, versioned like every legal document) or a registered optional script; packages describe their cookies in `Contracts\CookieCatalog` and register scripts that need consent in `Contracts\ConsentScripts` (never load such a script directly). Consents go only through `Cookies\ConsentRegistry` (`cookie_consents`, no IP or personal data); policy Markdown is rendered only through `Cookies\PolicyMarkdown` (raw HTML stripped). All legal documents (cookie policy, privacy policy, GDPR notice: `Enums\LegalDocumentType`) are versioned only through `Legal\LegalDocuments` (`legal_documents`; consents keep the cookie policy's version number), the cookie policy shown on `admiro.cookies.policy` and linked by the cookie links (never in a zone's `legal_documents`), the others shown on Core routes `admiro.legal.*` and linked in zones only through `Legal\LegalLinks` (zone `legal_documents`, then `legal_links`); first versions of all policies come from `admiro:legal:seed`.
- **Audit**: every audited event maps to an entry only in `Audit\AuditEntries` (file log and `audit_events` table); panels record their own actions with `Audit\Events\AdminActionPerformed`. No e-mail addresses in entries.
- **Cache isolation**: Build zone cache keys only with `Zones\ZoneCacheKey`. Prefix cache keys with the zone (`zone:<zone>:...`) while the store is `database`; use `Cache::tags(['zone:<zone>', ...])` only on `redis` (`database` and `file` stores do not support tags). Never call a global `Cache::flush()`.

## Database & Models
`docs/baza-danych.md` is the source of truth (its status line says what is implemented). In short:
- **One place**: migrations of every table (Core and public zones) live in this package's `database/migrations/`; private packages keep their own (skeleton's `CLAUDE.md`, "Private Packages": nothing about them in this public repository, examples use neutral names such as `shop`), loaded by `AdmiroServiceProvider`; seeders are classes in `src/Database/Seeders/` run by Core commands (`admiro:localization:seed`). Production blocks destructive DB commands; demo seeders refuse to run there.
- **Schema**: `Columns::base($table)` → domain columns → `Columns::closing($table, i18n: ...)` (`Database\Columns`, plain static methods — no Blueprint macros), then `app(History::class)->create($table)` (`<table>_history`; `->sync()` after column changes, `->drop()` in `down()`) and `app(IdSlots::class)->reserve($table)` (user ids from 1000, seed slots 1–999 via `IdSlots::next()`); `closing()` adds the global `json_default_settings` (read via `defaultSetting()`) and `json_tags`; `status` is a string backed by a PHP enum, flags are `boolean()` + `'boolean'` cast. Link tables have no standard columns but have history.
- **Models**: extend `Models\DataModel` (token, soft delete, standard casts, checksum, scopes `active()` and `default()` over the standard `is_active`/`is_default` flags; `HasI18n` for `json_i18n`); columns with a DB default repeat it in `$attributes`; no business logic and no `Auth` in models, no queries in controllers (`Queries/`, `Actions/`); every column has a cast and a `text_data` label (`lang/<locale>/data.php`); relations only in traits (`Models/Relations/`); public URLs use `token`, never `id`.
- **Organizations & permissions** (§15): `spatie/laravel-permission` with teams = `Models\Organization` (`organization_id`), configured by `Permissions\PermissionDefaults` (never publish `config/permission.php`); Core models `Models\Permissions\{Role,Permission,PermissionDenial}` with the full data standard on roles/permissions; zone accounts get roles and denials via `HasZonePermissions` (denial wins); check through `Contracts\ZonePermissionChecker` with the zone's guard; in a zone with `role_contexts` the signed-in account works in one active role per organization (`Contracts\CurrentRole`, `Permissions\RoleSelector`, set by `UseCurrentTeam`, switched on `account.role.switch`) and `HasZonePermissions` narrows its permissions to that role. No default organization (fail closed): the zone middleware `UseCurrentTeam` sets the request's organization (operator organization `Organization::OPERATOR_ID` for zones without `teams`, otherwise the account's chosen membership in `organization_members`); global roles need an explicit `organization_id => null`. Zone roles come only from JSON files (`database/seeders/permissions/<zone>.json`, private packages register their own via `PermissionFiles::add()`) synced by `admiro:permissions:sync`; protect routes with `ZonePermission::middleware()`, records of one organization extend `Models\OrganizationDataModel`, roles are granted only through `ZoneRoleAssignment` (no escalation, except roles delegated by the assigner's own roles in that organization: `assigns` in the roles file, `Permissions\RoleDelegation`; `SystemRoleGrant` only for console and provisioning). Organizations change only through `Organizations\OrganizationManagement` with `OrganizationData` (no tree cycles, operator organization protected; disabling never deletes — `setActive()` moves the record status active ↔ blocked; packages add per-organization badges to the panel tree through `Organizations\OrganizationBadges`; a new organization's billing e-mail defaults to its e-mail; departments — `is_department`, internal aggregation — only through `createDepartment()`, directly under a unit and with nothing under them; they are separate contexts for members and roles, while their data belongs to the unit: `Queries\Organizations\OrganizationUnits`, used by `OrganizationDataModel` binding); panels validate organization details with `Organizations\OrganizationForm` (NIP via `Rules\Nip`) and render them with `x-admiro::organization.fields` (organization, contact and address cards); people join an organization through `Organizations\EnrollMember`.
- **Localization dictionaries** (§14): tables `locale_*`, ISO columns `alpha_code_2`/`alpha_code_3`/`numeric_code` (`Database\CodeColumns`, `Contracts\DictionaryEntry::codeColumn()`), countries with ICU territory data (`Enums\Continent`, M49 region, population) sorted by continent; `Models\Dictionaries\{Country,Language,Currency,TaxRate,ExchangeRate}`, reads via `Queries\Dictionaries\{DefaultEntries,TaxRatesInForce,ExchangeRatesOn}`; days off per country come only from `Contracts\HolidayProvider` (Nager.Date) through `Holidays\HolidaySync` or `Holidays\ManualHolidays` and are read through `Queries\Dictionaries\HolidaysIn` (calendars mark them with `.ss-calendar__day--holiday`); exchange rates (PLN-based) come only from `Contracts\ExchangeRateProvider` (NBP table A) through `ExchangeRates\ExchangeRateSync` or `ExchangeRates\ManualExchangeRates`; interface languages via `Contracts\InterfaceLocales`, always within `APP_LOCALES`.

## Administrators' Zone (`src/Panel/`)
- **Core first**: the panel (`Simplysmart\Admiro\Panel\`) uses Core like any zone package: contracts (`Contracts\*`) and public base classes (`Zones\ZoneServiceProvider`, `Models\ZoneAccount`); Core code never references `Panel\`. A mechanism every zone could use (account creation `Console\CreateZoneAccountCommand`, the zone layout `x-admiro::zone.layout`) goes to Core, not to `Panel\`; the panel only configures it.
- **Service Provider**: `src/Panel/PanelServiceProvider.php` extends `ZoneServiceProvider`. Its `boot()` lets Core register the zone, then registers the zone menu, the onboarding listener and the account command; config (`zone` in `config/admiro.php`), views and texts are loaded by Core's provider under the shared `admiro` namespace.
- **Zone identity**: The zone and guard name come from `config('admiro.zone.name')`; the slug from `ADMIRO_SLUG`; the route-name prefix `admiro.` is fixed in `routeNamePrefix()` and never configurable. Always name the guard (`$zone->get()->guard` from `CurrentZone`), never `Auth::user()`.
- **Routes**: Relative paths and short names in `routes/panel/<tier>.php` (`account.php` = signed-in only; `zone.php` with `ZonePermission::middleware(Permission::...)`). Prefix, name prefix and middleware come from Core.
- **Admin panel**: controllers in `src/Panel/Http/Controllers/` (no queries there: Core queries `ZoneAccounts`, `ZoneRoleNames`, `ActiveOrganizations`), the signed-in admin and their permissions via `Panel\Http\AdminContext`, managed zone/account from the URL via `Panel\Http\ManagedAccounts` (unknown → 404). Acting on another admin needs `users.manage` plus `PermissionCoverage` (`Panel\Http\AdministratorGuard`); never on the own account. Organizations through Core `OrganizationManagement` and `OrganizationMembership` (members in `OrganizationMemberController`), settings through `LocalizationSettings`, dictionaries and VAT rates through `DictionaryManagement`, exchange rates through Core `ExchangeRateSync` / `ManualExchangeRates` (`ExchangeRateController`), the cookie policy, privacy policy and GDPR notice through Core `LegalDocuments` (`LegalDocumentController`, one page per `LegalDocumentType`, consent counts on the cookie policy; zone links via `legal_documents` in the config), days off through Core `HolidaySync` / `ManualHolidays` (`HolidayController`); every admin action is logged by `Panel\Http\AdminAudit` (Core `AdminActionPerformed`). - **Permissions**: `Panel\Enums\Permission` and `Panel\Enums\Role` mirror the roles file `database/seeders/permissions/admiro.json` (the only source of role assignments; the skeleton test `AdmiroPermissionsTest` keeps them equal). Labels are Core texts `permissions.admiro.*` / `roles.admiro.*`. Admins always sign in with the e-mailed code (trusted devices off unless `ADMIRO_TRUSTED_DEVICES=true`).
- **Database**: The `admiro_*` tables come from the Core migration `create_admiro_tables` (`ZoneTables`); `Models\AdmiroAccount` only sets `$table` and keeps its class name (`Simplysmart\Admiro\Models\AdmiroAccount` is stored as `model_type` in the permission tables — never move or rename it without a data migration).
- **Onboarding**: the onboarding overview `onboarding.index` (built on Core's checklist components `x-admiro::checklist.progress` / `x-admiro::checklist.steps` / `x-admiro::checklist.card` — the progress card with the next task, also on zone dashboards — with `View\Checklist\ChecklistItem`, shared with zone task lists; `Panel\Http\Controllers\OnboardingController`, page header with the progress card, all `Panel\Enums\OnboardingStep` panels — order, route, permission, milestones — with the done ones marked; step 1 „Installation” has no milestones and is done from the start, and its wizard page shows the installation guide `Panel\Onboarding\InstallationGuide` (stages with commands); ## Developer Tools (`src/Tools/`)
The package also ships the ecosystem's developer toolbox (formerly `simplysmart/tools`), the single release and deployment implementation for the skeleton and every package — never copy it elsewhere. Entry point `vendor/bin/simplysmart <command>` (`list`, `release`, `private:install`, `deploy:lock`, `deploy`, `deploy:onboarding`, `deploy:fresh`); `bin/version-release` and `bin/composer-private` stay as aliases. Details: `docs/narzedzia.md`.
- **Plain PHP CLI**: `src/Tools/` (`Simplysmart\Admiro\Tools\`) runs on the developer machine before and without Laravel: no framework, Core or zone classes, no dependencies beyond PHP; no service provider loads it.
- **Layout**: `bin/` holds thin entry points that only compose objects; `Tools/Console/` parses options and prints messages; `Tools/Release/` the SemVer release from `## [Unreleased]` (`CHANGELOG.md`/`VERSION` I/O); `Tools/PrivatePackages/` the private-package installer and deploy manifest (composer behind `ComposerRunner`, remotes via `RepositorySource`); `Tools/Deploy/` deployment (`EnvFile` parses config without a shell, `RemoteScript` quotes every value through `ShellArgument`, `RepositoryCheck`, `DeployMode`; `ProjectConfig` — `deploy <project>` from a base project with `infrastructure/deploy-vendors/<project>.env`: fresh manifest, pre-production on this machine through the same server script with `DEPLOY_KEEP_ENV=1`, then a yes/no question — `Closure` injected by `bin/simplysmart`, no terminal = no — before production); `Tools/Process/` runs git/scp/ssh behind `ProcessRunner`; `resources/deploy/remote.sh` is the server script streamed over `ssh … 'bash -s'`; `resources/boost/skills/` the shared AI skills.
- **Safety first**: Exit code `0`/`1`, errors to STDERR as clear Polish messages. `version-release`, `deploy*` have `--dry-run` (nothing written, sent or run on the server); `version-release` refuses MAJOR without `--major-confirm`; `deploy:fresh` (`migrate:fresh` on the server) runs only with `--confirm=<DEPLOY_SSH>`, and `remote.sh` lifts Core's destructive-command block (`ADMIRO_ALLOW_DESTRUCTIVE_COMMANDS=true`) only for that one process. File writes stay atomic (temporary file, then `rename()`).
- **Shared AI skills**: `resources/boost/skills/<name>/SKILL.md` (`solid-dry`, `docs-after-tests`, `changelog-before-commit`) is their single source; Laravel Boost copies them into a host project's `.claude/skills/` (`boost.json` → `packages: ["simplysmart/admiro"]`, then `php artisan boost:update`). Keep them project-agnostic and format Markdown with a blank line after every heading.


## Routing & URL Conventions
The skeleton's `CLAUDE.md` section "Routing & URL Conventions" is the source of truth; in short:
- **Clean signatures**: Controllers, actions and Form Requests never accept `$locale` or a zone slug; use `App::getLocale()`.
- **Shared localization**: Core owns the single localization middleware (`App::setLocale()`, `URL::defaults()`, `forgetParameter('locale')`) and the locale-mode logic (one locale → no prefix; several → `{locale}` always). Zone packages only attach it.
- **Core routes**: Core's own routes are relative paths with short names, registered by `Providers\CoreRoutesServiceProvider` with the `{locale}` prefix from `Localization\LocaleRouting::prefix()`/`where()` (shared with zones) and `SetLocale` + `SecurityHeaders` (no session): `routes/web.php` with the fixed name prefix `admiro.` (cookie policy and consent `admiro.cookies.*`, legal documents `admiro.legal.*`) and `routes/design-system.php` with the fixed name prefix `simplysmart.` (the design system page `simplysmart.design-system`, enabled outside production by `DESIGN_SYSTEM_PAGE`, checked per request). The administrators' zone shares the `admiro.` name prefix, so its route names must never repeat a Core route name (`cookies.*`, `legal.*`); zone slugs and zone route-name prefixes belong to the zones.
- **Named routes only**: Generate links with `route()`, never hand-built URLs containing the locale or slug.

## AI Skills

## Testing & Quality
Run in this directory before finishing (`composer install` first):
- `composer lint` — style, strict types and header (`composer format` fixes them).
- `composer analyse` — PHPStan at level `max` (`phpstan.neon`: `src/`, `config/`, `routes/`, `bin/`, `tests/`). Fix the cause; no ignores or baseline.
- Intelephense — no diagnostics in changed files (see the skeleton's Quality Gates).
- `composer test` — PHPUnit for the developer tools (`tests/Tools/`); tests run releases and deployments only in temporary directories with stubbed processes — never against a real project or server.
- Core and zone integration tests live in the skeleton's `tests/Feature/` (Core in `PackageIntegrationTest` and per area, the administrators' zone in `tests/Feature/Admiro/`; `composer test` in the skeleton root).
